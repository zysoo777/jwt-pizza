# Incident: 2026-04-07 10-53-00

## Summary

Between approximately 10:53 MST and 13:49 MST on 2026-04-07, users experienced failures when attempting to place pizza orders. The `/api/order` endpoint returned HTTP 500 errors because the Pizza Factory service remained in an active chaos state.

Although the incident appeared to be resolved shortly after initial mitigation, the chaos condition was still active in the Pizza Factory system. The issue was later re-investigated and fully resolved by identifying and using the correct recovery mechanism.

This was a medium-severity incident because it directly impacted the core user workflow of placing orders.

## Detection

The incident was first detected at approximately **10:53 MST** when the **JWT Pizza HTTP 500 Alert** fired and a mobile OnCall notification was received.

The issue was confirmed by observing repeated HTTP 500 failures from the `/api/order` endpoint.

After initial recovery actions, the system appeared to be functioning normally. However, at approximately **13:49 MST**, it was discovered that the Pizza Factory was still in a chaotic state, indicating that the issue had not been fully resolved.

## Impact

Between **10:53 MST and 13:49 MST**, users attempting to place orders experienced intermittent or persistent failures depending on the state of the Pizza Factory chaos condition.

Users experienced:

- failed order creation
- HTTP 500 responses
- unreliable checkout behavior

## Response

After the alert fired, the incident was investigated using Grafana alerts, browser developer tools, and the Pizza Factory dashboard.

The initial response focused on disabling chaos through an assumed backend API endpoint, but this approach failed because the endpoint did not exist.

The incident appeared resolved at first, but the Pizza Factory dashboard later revealed that chaos was still active.

During the second investigation, the source code in `orderRouter.js` was reviewed. It was discovered that failed Pizza Factory responses included a `followLinkToEndChaos` support link.

A local request to `/api/order` was used to retrieve the full response body, which contained the support report URL. Opening that link successfully resolved the chaos condition.

## Root cause

The root cause was an active chaos condition in the Pizza Factory service, which caused downstream order fulfillment requests to fail.

The main issue was that the correct recovery method was not immediately obvious. The system required the use of a support report link returned in the failed response, but this information was not clearly visible in the production environment.

This led to an initial false assumption that the issue had been resolved.

## Resolution

The incident was fully resolved by extracting and using the Pizza Factory support report link from a failed order response.

The recovery process was:

1. reproduce the failure locally using `/api/order`
2. capture the response containing `followLinkToEndChaos`
3. extract the support report URL
4. open the link in a browser to resolve chaos

Example response:

```json
{
  "message": "Failed to fulfill order at factory",
  "followLinkToEndChaos": "https://pizza-factory.cs329.click/api/support/.../report/..."
}
```
Opening the link returned:

```json
{
  "message": "Problem resolved. Pizza is back on the menu!"
}
```
This confirmed that the chaos condition in the Pizza Factory service had been successfully resolved.

- successfully placing follow-up orders  
- observing the HTTP 500 alert return to **Normal**  
- confirming the mobile alert moved to **Resolved**

## Prevention

This incident showed that recovery paths are not always obvious from alerts or the UI alone.

To improve future response:

- make chaos state more visible in the UI  
- expose recovery links more clearly  
- add alerts specifically for order failures  
- reduce reliance on hidden recovery mechanisms in API responses
